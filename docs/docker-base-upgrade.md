# Staged Debian 12 base-image upgrade

Debian 11 community LTS ended on 2026-08-31. Bookworm LTS is scheduled
through 2028-06-30. This change prepares a Python 3.14 / Debian 12 base;
it does not switch the default application image to an unpublished base.

## Stage 1: build and publish the base

This PR updates `Dockerfile-base` and `setup.sh` for Bookworm. The application
Dockerfile retains the existing published `hhyo/archery-base:sha-d8159f4`
reference and the Bullseye archive workaround needed to build that image.
APT signature verification remains enabled. Archive sources are a temporary
compatibility measure, not ongoing community security support.

For pull requests, CI validates both the default pinned application image and
an application built with the candidate Bookworm base. Candidate images are
local to the runner and are not published. Both get network-disabled smoke
checks with explicit Debian and Python expectations. The existing pinned image
remains Python 3.11; the candidate is Python 3.14.

After maintainer approval and merge, the base-image workflow publishes
`hhyo/archery-base` with the SHA tag generated by `docker/metadata-action`.
Maintainers must verify the successful publish job, its exact generated tag,
registry digest, and amd64 manifest before advancing to stage 2. Do not infer
the published tag from this PR's head: the merge commit/tag can differ.

## Stage 2: pin the published base in a follow-up PR

Once that artifact exists, open a separate PR to:

1. Replace `BASE_IMAGE` with the verified published `hhyo/archery-base:sha-...`
   tag, preserving the fixed-SHA release model. Record its registry digest.
2. Change the default-image smoke expectation from `bullseye` to `bookworm`.
3. Remove the Bullseye archive workaround and transitional duplicate candidate
   build once the pinned image is confirmed to use Bookworm.
4. Run full image builds, the native-driver smoke checks and normal CI before
   requesting review. Deployment is a separate operation.

No placeholder SHA, moving `latest` tag, or automatically selected unpublished
base should be committed. Stage 1 alone leaves the application on Bullseye;
the security-baseline migration is complete only after stage 2.

## Local validation without publishing

```sh
docker build --platform linux/amd64 -f src/docker/Dockerfile-base -t archery-base:bookworm-ci .
docker build --platform linux/amd64 -f src/docker/Dockerfile --build-arg BASE_IMAGE=archery-base:bookworm-ci -t archery:bookworm-ci .
docker run --rm --network none --entrypoint bash -e EXPECTED_DEBIAN_CODENAME=bookworm archery:bookworm-ci /opt/archery/src/docker/smoke-test.sh
```

The smoke script imports MySQLdb, LDAP, psycopg2, pyodbc and oracledb; loads the
Oracle thick client and ODBC driver; checks nginx configuration, SQLAdvisor
libraries, and utility help/version commands. It opens no database connections
and starts no application, worker or business task.

Microsoft's Debian 12 repository package installs its signing key and source
configuration. Percona Toolkit uses the dedicated `pt` repository rather than
the obsolete Percona Server 5.7 repository. Setup-script changes trigger base CI.

The image remains amd64 due to bundled tools and the Oracle client. Legacy
Mongo shell and other tool versions are unchanged. Live database/SSO validation
is separate. No application model changes are introduced. The Django 5.2 upgrade still
requires the usual migration review and `manage.py migrate` against a backed-up
application database during an approved rollout; do not assume framework
migrations are unnecessary. Keep the previously deployed
image digest available for rollback; no running stack is updated by this PR.

## Python 3.14 compatibility

Django 5.0 does not support Python 3.14. Use Django 5.2 LTS (at least 5.2.8),
with CI covering Python 3.11, 3.12 and 3.14. The default pinned application
therefore also receives Django 5.2 before its Python/OS base is switched.

Replace removed `STATICFILES_STORAGE` with `STORAGES`, keeping the existing
forgiving manifest backend and the default filesystem upload backend.
Regression checks cover copying/rendering template contexts and the configured
storage backends. Data-dictionary test mocks now return serializable metadata,
matching the real engine contract rather than relying on MagicMock encoding.

Debian 12 is retained while the Debian 13 choice awaits maintainer confirmation.
This avoids adding Trixie's `libaio1t64`/Oracle 19.21 loader issue to the Python
migration. No manual library compatibility symlink is installed. Legacy Mongo
shell issues are unchanged and must not be described as validated live support.
The security-driver updates in #3270 and Action updates in #3271 remain separate;
this PR must pass independently before combined validation after rebasing.
