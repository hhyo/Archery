## 1. Предпосылки и цели

По сравнению с Oracle, SQL Server и другими СУБД у MySQL есть свои сильные и слабые стороны на уровне ядра. При работе с MySQL нужно следовать определённым правилам, чтобы использовать преимущества и избегать рисков. Этот документ помогает разработчикам (RD), тестировщикам (QA) и эксплуатационным инженерам (OP) проектировать БД под online-нагрузки. Нормативы охватывают процесс изменений, проектирование таблиц и написание SQL — чтобы бизнес-системы работали стабильно и надёжно.

## 2. Нормативы проектирования

### 2.1 Проектирование базы данных

Все правила ниже помечены уровнями 【критично】, 【обязательно】 и 【рекомендация】 — приоритет соблюдения от высшего к низшему.

Проекты, не удовлетворяющие уровням 【критично】 и 【обязательно】, DBA возвращает на доработку.

### 2.1.1 Имя базы

1. 【обязательно】Имя базы — не более 32 символов. Имена связанных таблиц модуля по возможности отражают join-связь, например `user` и `user_login`.
2. 【обязательно】Формат имени базы: `имя_бизнес_системы_имя_подсистемы`. Таблицы одного модуля по возможности используют единый префикс.
3. 【обязательно】Имя шарда обычно: `базовое_имя_номер`, номер с 0, например `wenda_001`. Для шардирования по времени: `базовое_имя_время`.
4. 【обязательно】При создании БД явно указывать кодировку: только `utf8` или `utf8mb4`. Пример: `create database db1 default character set utf8;`.

### 2.1.2 Структура таблиц

1. 【обязательно】Имена таблиц и столбцов — не более 32 символов; только буквы, цифры и подчёркивание; только нижний регистр.
2. 【обязательно】Имя таблицы должно явно относиться к модулю, например префикс `sz` для системы преподавателей, `qd` для каналов и т.п.
3. 【обязательно】При создании таблицы явно указывать кодировку `utf8` или `utf8mb4`.
4. 【обязательно】При создании таблицы явно указывать движок хранения. Без особой необходимости — всегда InnoDB. Движки кроме InnoDB/MyISAM/Memory в production только после согласования с DBA. InnoDB поддерживает транзакции, row-lock, восстановление после сбоев, MVCC и другие важные свойства реляционных СУБД — это самый распространённый движок MySQL, поэтому он рекомендуется в первую очередь.
5. 【обязательно】У таблицы должен быть `COMMENT`.
6. 【рекомендация】По первичному ключу: (1) PK обязателен как `id` типа `int` или `bigint` с `auto_increment`; (2) поле, идентифицирующее бизнес-сущность строки, не делать PK — лучше `user_id`, `order_id` и т.п. с unique-индексом (см. дизайн `cdb.teacher`). Если PK заполняется случайными значениями, InnoDB дробит page и даёт много случайного I/O — производительность падает.
7. 【рекомендация】У ключевых таблиц (пользователи, деньги) должны быть `create_time` и `update_time` для расследования инцидентов.
8. 【рекомендация】Все столбцы — `NOT NULL`, при необходимости задавать `DEFAULT`. NULL занимает лишнее место в каждой строке, усложняет миграции и искажает агрегаты.
9. 【рекомендация】Большие поля (`blob`, `text`) выносить вертикально в отдельные таблицы и читать только когда нужно.
10. 【рекомендация】Денормализация: часто join-имые поля дублировать в других таблицах (например `user_name` в `user_account`, `user_login_log`), чтобы меньше join.
11. 【обязательно】Промежуточные таблицы (временные результаты) — префикс `tmp_`. Резервные/снимочные — префикс `bak_`. И те, и другие регулярно чистить.
12. 【обязательно】`ALTER TABLE` для таблиц > 1 млн строк — только после ревью DBA и в низкий трафик. `ALTER` берёт table lock и блокирует все записи — сильный риск для бизнеса.

### 2.1.3 Оптимизация типов столбцов

1. 【рекомендация】Для `auto_increment` предпочтителен `bigint`. Беззнаковый `int` примерно до 2.1 млрд (`-2147483648~2147483647`); переполнение приводит к ошибке.
2. 【рекомендация】Для полей с малой кардинальностью (`status`, `type`) — `tinyint` или `smallint`, чтобы экономить место.
3. 【рекомендация】IP хранить как `int`, не как `char(15)`. `int` — 4 байта, `char(15)` — минимум 15. На 100 млн строк это ~1.1 ГБ лишнего. SQL: `select inet_aton('192.168.2.12'); select inet_ntoa(3232236044);` PHP: `ip2long('192.168.2.12'); long2ip(3530427185);`
4. 【рекомендация】Избегать `enum` и `set`: тратят место, значения зашиты, менять неудобно. Лучше `tinyint` / `smallint`.
5. 【рекомендация】Избегать `blob`/`text`: они тяжелы по диску и памяти. При загрузке таблицы большие поля попадают в память и бьют по производительности. Уточните у PM/RD, действительно ли нужны такие поля. В InnoDB при строке > 8098 байт самый длинный столбец частично (768 байт) остаётся в исходной page, остаток — в `overflow-page`; в формате `compact` загружаются обе.
6. 【рекомендация】Деньги хранить как `int`, на стороне приложения умножать/делить на 100. `int` — 4 байта, `double` — 8.
7. 【рекомендация】Текст по возможности в `varchar` (переменная длина, экономичнее `char`). На уровне MySQL server максимум 65535 байт текстовых данных в строке; в utf8 — до 21844 символов, иначе авто-конверсия в `mediumtext`. `text` в utf8 — до 21844, `mediumtext` — до 2^24/3, `longtext` — до 2^32 символов. Обычно `varchar` и не более ~2700 символов.
8. 【рекомендация】Время — предпочтительно `timestamp` (`datetime` — 8 байт, `timestamp` — 4, диапазон `1970-01-01 00:00:01` … `2038-01-01 00:00:00`). Более продвинутый вариант — `int` + `unix_timestamp()` / `from_unixtime()`.

### 2.1.4 Проектирование индексов

1. 【обязательно】У InnoDB PK: `id int/bigint auto_increment`; значение PK обновлять запрещено.
2. 【рекомендация】Имена: PK — с `pk_`, unique — с `uk_` или `uq_`, обычный индекс — с `idx_`; нижний регистр; суффикс — имя/аббревиатура таблицы или поля.
3. 【обязательно】Для InnoDB и MyISAM тип индекса — `BTREE`; для MEMORY — `HASH` или `BTREE` по необходимости.
4. 【обязательно】Длина одной индексной записи ≤ 64 KB.
5. 【рекомендация】Не более 7 индексов на таблицу.
6. 【рекомендация】Предпочитать составные индексы; поле с наибольшей селективностью — первым. Селективность `userid`: `select count(distinct userid)`.
7. 【рекомендация】В multi-table join на join-столбце ведомой таблицы должен быть индекс — иначе join дорогой.
8. 【рекомендация】Не допускать избыточных индексов. Если есть `key(a,b)`, то `key(a)` избыточен и подлежит удалению.

### 2.1.5 Шардирование и партиционирование

1. 【обязательно】У партиционированной таблицы поле `partition-key` должно быть проиндексировано или быть первым столбцом составного индекса.
2. 【обязательно】Число партиций (включая подпартиции) ≤ 1024.
3. 【обязательно】До релиза RD или DBA должны задать стратегию создания и очистки партиций.
4. 【обязательно】SQL к партиционированной таблице должен включать ключ партиции.
5. 【рекомендация】Файл одной партиции ≤ 2 ГБ, суммарно ≤ 50 ГБ; желательно ≤ 20 партиций.
6. 【обязательно】`ALTER TABLE` по партиционированной таблице — только в низкий трафик.
7. 【обязательно】При шардировании по БД число баз ≤ 1024.
8. 【обязательно】При шардировании по таблицам число таблиц ≤ 4096.
9. 【рекомендация】Один шард-таблица ≤ 5 млн строк, файл ibd ≤ 2 ГБ — так распределённые данные работают лучше.
10. 【рекомендация】Горизонтальный шардинг предпочтительно по модулю; логи/отчёты — по дате.

### 2.1.6 Кодировка

1. 【обязательно】Кодировка БД, таблиц и столбцов должна совпадать: `utf8` или `utf8mb4`.
2. 【обязательно】Кодировка приложения / переменных окружения должна совпадать с БД и таблицами — единообразно `utf8`.

### 2.1.7 Рекомендации по DAO-слою приложения

1. 【рекомендация】В новом коде не опираться на ORM-model: предпочтительнее ручной SQL + bind-параметры. Model удобен ООП-стилем, но легко порождает сложный SQL и дорогие приведения типов — нагрузка на БД растёт.
2. 【рекомендация】Подключения к MySQL/Redis: обязательны timeout и переподключение при сбое с интервалом между попытками.
3. 【рекомендация】В ошибках приложения по возможности показывать исходные сообщения MySQL/Redis — так проще диагностировать.
4. 【рекомендация】При connection pool обязательно настроить initial/min/max, timeout и утилизацию соединений под бизнес; иначе исчерпаете пул и получите инцидент.
5. 【рекомендация】Для таблиц log/history заранее (до релиза) согласовать с RD/DBA схему очистки или архивации — они быстро растут.
6. 【рекомендация】На этапе дизайна RD должен учесть lag master/replica. Кратковременный lag (до ~20 с) не должен ломать бизнес: строго консистентные чтения — в транзакции на master, либо читать с replica с задержкой после обновления.
7. 【рекомендация】При конкурентном доступе к одним данным (InnoDB) возможны row/table lock. UPDATE по возможности по первичному ключу.
8. 【рекомендация】Порядок захвата блокировок в бизнес-логике держать одинаковым — иначе deadlock.
9. 【рекомендация】Если у строк/столбцов ratio read:write > 10:1, горячие данные можно класть в кэш (memcached/redis), чтобы снизить давление на MySQL.

### 2.1.8 Пример корректного CREATE TABLE

Пример относительно корректного оператора создания таблицы:

    CREATE TABLE user (
      `id` bigint(11) NOT NULL AUTO_INCREMENT,
      `user_id` bigint(11) NOT NULL COMMENT 'ID пользователя',
      `username` varchar(45) NOT NULL COMMENT 'Настоящее имя',
      `email` varchar(30) NOT NULL COMMENT 'Email пользователя',
      `nickname` varchar(45) NOT NULL COMMENT 'Никнейм',
      `avatar` int(11) NOT NULL COMMENT 'Аватар',
      `birthday` date NOT NULL COMMENT 'День рождения',
      `sex` tinyint(4) DEFAULT '0' COMMENT 'Пол',
      `short_introduce` varchar(150) DEFAULT NULL COMMENT 'Краткое описание, до 50 иероглифов',
      `user_resume` varchar(300) NOT NULL COMMENT 'Путь к резюме пользователя',
      `user_register_ip` int NOT NULL COMMENT 'IP при регистрации',
      `create_time` timestamp NOT NULL COMMENT 'Время создания записи',
      `update_time` timestamp NOT NULL COMMENT 'Время изменения профиля',
      `user_review_status` tinyint NOT NULL COMMENT 'Статус модерации: 1 — ок, 2 — на проверке, 3 — отклонено, 4 — ещё не отправлено',
      PRIMARY KEY (`id`),
      UNIQUE KEY `idx_user_id` (`user_id`),
      KEY `idx_username`(`username`),
      KEY `idx_create_time`(`create_time`,`user_review_status`)
    ) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='Базовая информация пользователя сайта';

## 2.2 Написание SQL

### 2.2.1 DML-операторы
1. 【обязательно】В SELECT явно перечислять столбцы, запрещён `*`. `select *` читает лишнее и нагружает сеть; при изменении схемы без синхронизации model система падает.
2. 【обязательно】В INSERT явно указывать столбцы, не писать `insert into t1 values(…)`.
3. 【рекомендация】В `insert into…values(XX),(XX),(XX)…` число наборов значений ≤ 5000. Большие батчи ускоряют запись, но вызывают lag репликации.
4. 【рекомендация】Вместо `UNION` предпочитать `UNION ALL`, число веток ≤ 5. `UNION ALL` без дедупликации экономит ресурсы.
5. 【рекомендация】Список `IN` ≤ 500 значений, например `select… where userid in(….до 500…)`, чтобы уменьшить сканирование и ускорить запрос.
6. 【рекомендация】Массовые UPDATE в транзакции — порциями с паузами (sleep): мало и часто.
7. 【обязательно】Все таблицы транзакции — InnoDB. Иначе при ошибке не будет полного rollback и возможна остановка репликации.
8. 【обязательно】Запись и транзакции — на master; read-only SQL — на replica.
9. 【обязательно】Кроме статических/маленьких таблиц (≤ 100 строк) у DML должен быть WHERE с использованием индекса.
10. 【обязательно】В production запрещены hint: `sql_no_cache`, `force index`, `ignore key`, `straight join` и т.п. Hint навязывает план, а с ростом данных он может устареть — доверяйте оптимизатору MySQL.
11. 【обязательно】Типы полей слева и справа от `=` в WHERE должны совпадать, иначе индекс не используется.
12. 【рекомендация】У `SELECT|UPDATE|DELETE|REPLACE` должен быть WHERE, и условия WHERE должны использовать индекс.
13. 【обязательно】На больших таблицах в production полноскановые запросы крайне нежелательны; для статических таблиц < 100 строк допустимы. Объём выборки не должен превышать ~25% строк таблицы, иначе индекс не поможет.
14. 【обязательно】В WHERE запрещён только полноразмытый `LIKE` без других условий равенства/диапазона — иначе индекс не используется.
15. 【рекомендация】Не применять функции/выражения к индексным столбцам: `where length(name)='Admin'` или `where user_id+2=10023` — индекс не сработает.
16. 【рекомендация】Меньше `OR`: можно заменить на `UNION` и индексы на каждом условии. Пример: `where a=1 or b=2` → `where a=1… union …where b=2` при `key(a), key(b)`.
17. 【рекомендация】Пагинация с большим offset: сначала фильтровать. `select a,b,c from t1 limit 10000,20;` → `select a,b,c from t1 where id>10000 limit 20;`.

### 2.2.2 Соединения нескольких таблиц

1. 【обязательно】Запрещены join между разными БД — это снижает связность модулей и готовит почву к разбиению БД.
2. 【обязательно】Запрещены join в update-SQL бизнеса, например `update t1 join t2…`.
3. 【рекомендация】Подзапросы нежелательны: лучше разбить на несколько запросов в приложении или заменить join.
4. 【рекомендация】В online не более 3 таблиц в join.
5. 【рекомендация】В multi-table join использовать алиасы; в SELECT ссылаться на поля через алиас / `db.table`, например `select a from db1.table1 alias1 where …`.
6. 【рекомендация】В join драйвером выбирать таблицу с меньшим результирующим набором.

### 2.2.3 Транзакции
1. 【рекомендация】В транзакции число строк, затрагиваемых `INSERT|UPDATE|DELETE|REPLACE`, ≤ 2000; число параметров в `IN` WHERE ≤ 500.
2. 【рекомендация】При пакетной обработке контролировать интервал между транзакциями (sleep), обычно 5–10 секунд.
3. 【рекомендация】Для вставок в таблицы с `auto_increment` конкурентность ≤ 200.
4. 【обязательно】Дизайн должен учитывать уровень изоляции транзакций: dirty read, non-repeatable read, phantom read. Online рекомендуется `repeatable-read`.
5. 【рекомендация】Не более 5 SQL в одной транзакции (кроме платёжных сценариев). Длинные транзакции долго держат блокировки и перегружают кэш/соединения MySQL.
6. 【рекомендация】UPDATE по возможности по PK или unique key: `update … where id=XX`. Иначе gap lock расширяет область блокировки, падает производительность, растут deadlock.
7. 【рекомендация】Внешние вызовы (webservice, файловое хранилище) по возможности выносить из транзакции, чтобы она не растягивалась.
8. 【рекомендация】SELECT, критичные к lag master/replica, выполнять в транзакции с принудительным чтением с master.

### 2.2.4 Сортировка и группировка

1. 【рекомендация】Меньше `ORDER BY`: с бизнесом согласовать отказ от сортировки или перенос её в приложение. `ORDER BY` / `GROUP BY` / `DISTINCT` дорого стоят CPU, а CPU БД — дефицитный ресурс.
2. 【рекомендация】Для `ORDER BY` / `GROUP BY` / `DISTINCT` стараться получать уже упорядоченные данные по индексу. Пример: `where a=1 order by b` может использовать `key(a,b)`.
3. 【рекомендация】Если запрос содержит `ORDER BY` / `GROUP BY` / `DISTINCT`, результат после WHERE держать ≤ 1000 строк, иначе SQL будет медленным.

### 2.2.5 Запрещённые SQL в production

1. 【критично】Запрещены `update|delete t1 … where a=XX limit XX;` с `LIMIT` без `ORDER BY PK` — риск рассинхрона master/replica и порчи данных. Добавляйте `ORDER BY PK`.
2. 【критично】Запрещены коррелированные подзапросы вида `update t1 set … where name in(select name from user where…);` — крайне низкая эффективность.
3. 【обязательно】Запрещены procedure, function, trigger, views, event и внешние ключи: они расходуют ресурсы и снижают масштабируемость инстанса. Реализуйте логику в приложении.
4. 【обязательно】Запрещён `insert into … on duplicate key update…` при высокой конкуренции — риск рассинхрона master/replica.
5. 【обязательно】Запрещены multi-table update вида `update t1,t2 where t1.id=t2.id…`.
